# Documentation Policy

## Documentation map

`CUSTOMISE: Identify the audiences, document roots, generated references, architecture records, API documentation, operator guides, release notes, and ownership.`

## Authority

Specifications and approved decision records define intended behaviour. Executed tests and inspected implementation provide evidence of actual behaviour. Documentation must clearly distinguish current, planned, deprecated, and unsupported behaviour.

## Required updates

Update documentation when a change affects public behaviour, configuration, interfaces, build or test procedures, deployment, operations, diagnostics, compatibility, resource budgets, hardware assumptions, security, or safety.

## Generated documentation

`CUSTOMISE: Record source files, generators, commands, checked outputs, and the rule that generated files are not manually edited.`

## Style

`CUSTOMISE: Terminology, voice, spelling convention, structure, examples, diagrams, link policy, and documentation lint rules.`

## Validation

Run the configured documentation checks. Verify commands and examples where practical. Check links, generated artefacts, version references, and terminology. Do not claim functionality that has not been implemented and verified.
